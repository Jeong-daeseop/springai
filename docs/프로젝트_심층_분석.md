### 1.3 LLM 라우팅 — 이중 구조 문제

프로젝트에 완전히 독립적인 두 가지 라우팅 메커니즘이 존재합니다.

**메커니즘 A: `LlmRouterService`** (`service/LlmRouterService.java:18`)
- 사용처: `ToolApiController`, `RagController` (REST API)
- 라우팅 기준: `taskType` 문자열 (CLASSIFICATION/SIMPLE_QUERY → OpenAI, SENSITIVE_DATA → Ollama)
- 방식: 원시 `ChatModel.call()` — 스트리밍 없음, 메모리 없음, RAG 어드바이저 없음
- 주의: CLAUDE taskType은 예외를 던짐 (실제 Claude 호출 불가)

**메커니즘 B: `selectClient()`** (`chat/service/impl/EgovSessionAwareChatServiceImpl.java:52`)
- 사용처: `EgovOllamaChatController` (웹 채팅 UI)
- 라우팅 기준: 모델명 접두사 (`gpt-*/o1*/o3*` → OpenAI, 그 외 → Ollama)
- 방식: `ChatClient` — 스트리밍, ChatMemory 어드바이저, QuestionAnswerAdvisor 포함

두 메커니즘은 완전히 독립적으로 진화하여 동기화가 불가능한 상태입니다.

## 2. 의존성 구조

### 2.1 주요 의존 관계

```
config/
  McpConfig         → 19개 Tool 클래스 (평면 주입)
  SecurityConfig    → AppProperties
  VectorStoreConfig → EmbeddingModel (TransformersEmbeddingModel 자동설정)
  OllamaConfig      → 독립적, OllamaChatModel 빈 수동 생성
  EgovRagConfig     → OllamaChatModel, OpenAiChatModel, VectorStore

chat/service/impl/
  EgovSessionAwareChatServiceImpl
    → ChatClient(openAi), ChatClient(ollama)
    → MessageChatMemoryAdvisor, QuestionAnswerAdvisor
    → EgovCompressionQueryTransformer
    → EgovPromptBuilder, ContextAssembler

service/
  ContextAssembler       → SchemaService, TableRelationService, GenerationHistoryService
  CrudPromptBuilderService → JdbcTemplate, CommonCodeService, EgovPromptBuilder
  RagService             → VectorStore, ChunkService, RedisTemplate
  LlmRouterService       → OpenAiChatModel, OllamaChatModel
```

### 2.2 순환 의존 여부

순환 의존 없음. 의존 그래프가 명확한 단방향 DAG 구조:
- Config 계층 → Service 계층 → Repository/Mapper 계층
- Tool 계층 → Service 계층 (단방향)

### 2.3 고결합도 지점

- `McpConfig.java:37-56`: 19개 Tool 클래스를 단일 빈 메서드에 주입. Tool 추가 시 이 메서드를 반드시 수정해야 함
- `EgovSessionAwareChatServiceImpl` 생성자: 7개 파라미터 — 높은 fan-in

## 3. 설정 구조 심층 분석

### 3.1 application.yaml 핵심 설정

| 설정 | 값 | 목적 |
|------|-----|------|
| `web-application-type: servlet` | HTTP 서버 활성화 | SSE 트랜스포트 사용 |
| `transport: sse` | SSE over HTTP | Claude Desktop 연결 방식 |
| `spring.ai.model.embedding: transformers` | ko-sroberta ONNX | 외부 임베딩 API 불필요 |
| `temperature: 0.0` | 결정적 출력 | 코드 생성 일관성 |
| `rag.similarity.threshold: 0.30` | 낮은 임계값 | PDF 변환 문서 대응 |
| `chat.memory.max-messages: 8` | 8개로 제한 | num-ctx 8192 토큰 예산 |
| `allow-bean-definition-overriding: true` | 빈 충돌 허용 | Ollama(채팅) + Transformers(임베딩) 공존 |

### 3.2 SecurityConfig 접근 제어

```
CSRF: /sse, /mcp/** 만 비활성화
Session: STATELESS
permitAll:  /sse, /mcp/**, /, /ai/**,
            /api/chat/**, /api/ollama/**, /api/documents/**
authenticated: /api/** (나머지)
denyAll: 그 외 모든 경로
```

**주의**: `/ai/**`, `/api/chat/**`은 인증 없이 LLM 채팅 엔드포인트 접근 가능 → API 비용 남용 위험

### 3.3 VectorStoreConfig 초기화

`config/VectorStoreConfig.java:31-48`:
- `JedisPooled(URI.create(redisUri))` — URI 방식으로 TLS/인증 지원
- `initializeSchema(true)` — 시작 시 Redis 인덱스 자동 생성
- 메타데이터 필드: `type` (tag), `docId` (tag)
- `RedisVectorStoreAutoConfiguration` 명시적 제외 (`SpringaiApplication.java:8`)

### 4.3 코드 품질 이슈

#### OllamaConfig vs application.yaml 설정 충돌

`OllamaConfig.java:56` — `temperature(0.3)` 수동 설정
`application.yaml:44` — `temperature: 0.0` YAML 설정

수동 빈이 자동설정을 덮어쓰므로 `num-predict`, `num-ctx` 등 YAML 설정이 **무시됨**.

#### 존재하지 않는 OpenAI 모델명

`application.yaml:84-86` — `gpt-5.4-mini`, `gpt-5.4` 설정
→ OpenAI API에 존재하지 않는 모델명, 실제 호출 시 오류 발생

#### 에러 응답 형식 불일치

| 위치 | 응답 형식 |
|------|----------|
| `ToolApiController.java:77` | `Map.of("error", message)` |

## 5. 미완료 및 개선 필요 영역

### 5.1 LLM 라우팅 이중 구조 통합

**현재 문제:**
- `LlmRouterService` (REST API용) + `selectClient()` (웹 채팅용) 이 완전 독립
- 한쪽 수정 시 나머지에 반영되지 않음
- `LlmRouterService`의 CLAUDE taskType은 예외를 던짐 (실제 동작 불가)

**권고 방향:**
`LlmRouterService`를 `ChatClient`를 반환하는 방식으로 개선하여 두 경로 통합

### 5.2 OllamaConfig 수동 빈 제거

`OllamaConfig.java` 삭제 후 Spring AI 자동설정에 위임
- temperature, num-ctx, num-predict 모두 YAML에서 일원 관리
- Reactor Netty 타임아웃은 YAML `spring.ai.ollama.chat.options.*` 으로 설정

### 5.3 쿼리 압축 비동기화

`EgovCompressionQueryTransformer.compress()` 의 Ollama 호출을
`Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` 으로 감싸
Reactive 파이프라인 블로킹 해소

### 5.4 한국어 단어 압축 임계값

`EgovCompressionQueryTransformer.java:117-119` — 2단어 미만 쿼리 압축 스킵
→ 한국어 단어 쿼리 (예: "COMTNEMPLYRINFO 스키마") 가 압축 누락될 수 있음

## 7. Trade-offs 요약

| 설계 선택 | 장점 | 단점 |
|-----------|------|------|
| LLM 라우팅 이중 구조 유지 | 변경 없음, 각 경로 독립 최적화 | 인지 부담 2배, 버그 동기화 불가 |
| 라우팅 단일화 | 단일 진실 공급원, 일관된 동작 | REST API + 채팅 동시 리팩토링 필요 |
| OllamaConfig 수동 유지 | HTTP 타임아웃 명시적 제어 | temperature 불일치, YAML 설정 무시 |
| OllamaConfig 삭제 | YAML 설정 일원화, 올바른 동작 | YAML로 타임아웃 재설정 필요 |
| 로컬 ONNX 임베딩 | 비용 0, 한국어 특화, 외부 무의존 | 대량 임베딩 시 속도 느림 |
| Redis 통합 (VectorStore+ChatMemory+세션) | 인프라 단순화 | Redis 단일 장애점 |
| 쿼리 압축 동기 블로킹 유지 | 구현 단순 | Reactive 파이프라인 1-5초 지연 |
| 비동기화 | 파이프라인 논블로킹 | boundedElastic 스레드 풀 관리 필요 |
