# 픽셀재현(claude 경로) 제외범위 — 1차 구현 제외 대상 영향검토

> [`Figma_픽셀재현_제외범위_구현계획.md`](./Figma_픽셀재현_제외범위_구현계획.md)의 트랙 A~D 각각에
> 명시된 "1차 구현 제외" 6개 항목에 대한 영향 검토. 구현 착수 여부를 판단하기 위한 분석 문서이며,
> 이 문서 자체는 코드 변경을 포함하지 않는다.

---

## 트랙 A — 구조 일치도 도구

| 항목 | 영향 범위 | 심각도 | 근거/완화책 |
|---|---|---|---|
| 실제 픽셀 스크린샷 diff(SSIM 등) | `compareDesignFidelity()` 결과가 "구조는 같은데 시각적으로는 다른" 케이스를 놓침(거짓 양성) | 중 | Tool 설명에 "구조적 일치도이며 시각적 일치 보장 안 함"을 명시하기로 되어 있어 오인 위험은 문서화로 일부 완화. 단, 스크린샷 캡처 인프라(PNG/BufferedImage) 자체가 없어 착수 비용이 이번 범위를 훨씬 초과 — 별도 프로젝트급 |
| `componentGeometry`(좌표) 비교 제외 | 두 화면의 실제 배치 위치 차이를 정량화 못함 | 낮음~중 | v1 목적(archetype/component/fieldRole/action 구조 일치)엔 불필요. 좌표 비교하려면 허용오차 설계가 별도 필요(트랙 D의 5px 오차 경험 재사용 가능) |

## 트랙 B — 이미지 asset 다운로드

| 항목 | 영향 범위 | 심각도 | 근거/완화책 |
|---|---|---|---|
| SVG 코드 자체 추출 제외(래스터만 처리) | 벡터 아이콘이 PNG/JPG로만 삽입 → 확대 시 깨짐, CSS로 색상(fill) 커스터마이징 불가 | 중 | KRDS가 자체 아이콘 폰트/스프라이트 체계를 쓸 가능성이 있어 실사용 임팩트는 제한적일 수 있음(**미검증 — 실제 KRDS 아이콘 처리 방식 확인 안 됨**). 완화책 없음 |
| 이미지 압축/리사이즈 제외 | 원본 크기 그대로 저장 → 저장소/페이지 로딩 성능 영향 | 낮음~중 | 10MB 상한 체크는 있어 무방비는 아님. 이미지 개수 적으면 영향 미미, 많으면 누적됨. 사용자가 후처리로 직접 최적화하는 수동 워크어라운드 존재 |

## 트랙 C — 반응형 대응

| 항목 | 영향 범위 | 심각도 | 근거/완화책 |
|---|---|---|---|
| 여러 viewport 실제 렌더링 검증 제외 | 프롬프트 가드레일 문구가 실제로 지켜졌는지 **자동으로 확인할 방법이 전무** — LLM이 문구를 무시하고 좌표를 고정 px로 하드코딩해도 시스템이 스스로 못 잡아냄 | **중~높음** | 유일한 방어선이 "문구"뿐이라는 구조적 약점. 다만 `captureWebPageMultiViewport()` Tool이 이미 존재하므로, 자동 판정 로직 없이도 "생성 직후 여러 viewport로 캡처해서 사람이 눈으로 확인"하는 저비용 수동 워크플로우는 지금 당장 가능 |

## 트랙 D — 반복 dedup

| 항목 | 영향 범위 | 심각도 | 근거/완화책 |
|---|---|---|---|
| 유사도 기반(퍼지) dedup 제외 | 이름이 다른데 시각적으로 반복되는 요소는 dedup 안 되고 트리에 그대로 남음 | 낮음 | 최악의 경우도 "프롬프트가 조금 더 길어진다" 수준이지 잘못된 결과를 유발하진 않음. 오탐(다른 의미 노드를 반복으로 오인) 방지를 위해 의도적으로 보수적으로 설계한 트레이드오프 |

---

## 종합 우선순위 제안

1. **트랙 C(반응형 실검증)** — 자동 검증 로직 신설보다, 이미 있는 `captureWebPageMultiViewport()`를 활용한 "생성 후 수동 확인 가이드"부터 문서화하면 낮은 비용으로 구조적 약점을 완화할 수 있음
2. **트랙 B(SVG 추출)** — 착수 전에 KRDS 아이콘 처리 방식부터 먼저 확인 필요(미검증 가정에 근거해 우선순위를 매기는 건 위험)
3. **트랙 A(좌표 비교), 이미지 압축, 트랙 D(퍼지 dedup)** — 현재 영향이 제한적이라 낮은 우선순위로 유지해도 무방
