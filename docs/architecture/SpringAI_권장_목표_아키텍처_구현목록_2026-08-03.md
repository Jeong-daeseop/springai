## 1. 상태 표기와 운영 규칙

| 표기 | 의미 |
|---|---|
| `[ ]` | 미착수 |
| `[-]` | 진행 중 |
| `[x]` | 구현과 완료 Gate 검증 완료 |
| `[!]` | 차단 또는 별도 결정 필요 |
| `[~]` | 코드 존재, 완료 Gate 미충족 |

운영 규칙:

- 클래스나 메서드가 존재한다는 이유만으로 `[x]`로 변경하지 않는다.
- 각 항목은 연결된 단위·통합·계약 테스트 또는 운영 증적이 있어야 완료된다.
- 상태 변경 시 증적 열 또는 작업 기록에 test/report/commit을 남긴다.
- 기존 코드에 일부 구현이 있어도 이 목록의 Gate를 다시 확인하기 전에는 `[~]` 또는 `[ ]`로 둔다.
- P0 항목이 `[!]`인 상태에서는 Release Gate를 승인하지 않는다.
- 이 문서는 전체 아키텍처의 집계 상태 원장이다. Figma·Thymeleaf 상세 원장의 개별 `[x]`가 있어도
  이 문서의 상위 완료 Gate가 열려 있으면 집계 상태는 `[~]`를 유지한다.

### 1.1 실행 승인 조건

- [x] 작업표와 Mermaid 선행조건이 일치한다.
- [x] WP2A 긴급 격리와 WP2B 안전 재구현이 분리됐다.
- [x] WP1 인증 위치를 `OncePerRequestFilter` + `RiskAwareToolCallbackProvider`로 확정했다.
- [x] dirty code fingerprint와 MCP snapshot hash를 구현계획서 §0.1에 기록했다.
- [x] multi-project 적용 여부와 WP2B 재구현 여부를 ADR로 종료할 수 있다.
- [x] 동시 리팩터링 파일의 stage·commit은 소유권 확정 전 금지한다.

이 승인은 계획 실행에 대한 승인이다. 현재 미커밋 코드 전체를 한 번에 stage하거나 commit하는 승인이
아니다.

   `[x]`). `board-jsp`는 핵심 메커니즘은 fabricated fixture로 검증했으나 이 pass와 무관한 사전
   결함 2건(bare `@RequestMapping`, VO 상속 미지원)으로 golden fixture 자체는 끝까지 통과 못함
   (`ARCH-0619` 여전히 `[ ]`, §10 3차 pass 실행 메모 참고).
9. `WP7` 2차 pass: 완료·커밋(`ff291b2`). `BEST_EFFORT_COMPATIBILITY`를 진짜 파일별 독립 처리로
   구현하고(`ARCH-0702`), CRUD Pipeline의 유일한 WRITE 어댑터 `CodeServiceGenerationExecutor`를
   공용 `ApprovedProjectWritePort`로 전환했다(`ARCH-0716`) — `outputPath` allowlist 검증은
   `CodeService.validateOutputRoot`로 유지, 레이어 순서 보존 회귀를 테스트로 잡아 수정, 기존 CRUD
   골든 테스트 전부 회귀 없이 통과(`ARCH-0724`). Board/Master-detail(`ARCH-0717/0718`)은 단일 파일
   write·바이너리 콘텐츠 미지원·skip/preserve 판정 결합 등 각기 다른 이유로 계속 보류, 단발성
   Tool(`ARCH-0719`)은 "생성 계획" 개념이 없어 전환 대상이 아님으로 확정. §11 2차 pass 실행 메모

10. `WP8` 1차 pass: 완료·커밋(`0c8d512`). `GateSeverity`(BLOCK/WARN) 정책과

   (`ARCH-0801/0805/0811`). 실제 Spring `TemplateEngine` render Gate(`ARCH-0804`)도 신규
   구현했으나 `@{...}`/`th:field`는 프로덕션 클래스패스에 없는 `spring-test` Mock 서블릿 없이는
   검증 불가함을 확인해 범위에서 제외(문서화·회귀 테스트로 고정). `GeneratedProjectBuildValidator`

   신규 추가해 반대 방향(MCP→REST→MCP)·source drift·동시 Apply(락 검증)·Apply 실패 rollback을
   전부 실제 REST/MCP 진입점으로 검증했다(`ARCH-0813/0815/0816/0818`). Playwright/axe/visual
   Gate(`ARCH-0808~0810`)는 외부 네트워크 접근은 확인됐으나 브라우저 인프라 구축이 별도 스코프로
   커야 해서 보류, Figma E2E(`ARCH-0817/0819~0822`)는 이 환경에 `FIGMA_ACCESS_TOKEN`이 없어
   검증 불가로 보류. §12 1차 pass 실행 메모 참고.
11. **다음**: BOARD golden fixture 사전 결함 수정(VO 상속 지원, `@RequestMapping` 명시적 method

> 파일 하나 때문에 이미 저장된 파일을 롤백하지 않음)인데, `ProjectChangeSet`은 "단일 project root +
> 상대경로 + 전부 아니면 전무" 모델을 전제한다. 이 둘을 억지로 맞추면 CRUD 생성의 기존 부분 성공
> 동작이 조용히 atomic rollback으로 바뀌는 실제 동작 변경이 된다 — 별도 설계 결정 없이 하지 않는다.
> `CodeServiceGenerationExecutor`가 이미 `GenerationExecutor` 인터페이스 뒤에 있어 나중에 전환할
> 진입점 자체는 준비돼 있다.

> **2차 pass 실행 메모(2026-08-05)** — 1차 pass의 "모델 불일치" 결론을 다시 조사한 결과 너무
> 성급했음을 확인했다: CRUD/Board/Master-detail 모두 한 번의 생성 호출 안에서는 **단일
> `outputPath`를 공유**하므로 `ProjectChangeSet`의 "단일 root + 상대경로" 모델과 실제로 잘 맞는다.
> 진짜 걸림돌은 `BEST_EFFORT_COMPATIBILITY`가 여태 이름만 있고 진짜 "파일별 독립 처리"를 구현하지
> 않았다는 점뿐이었다 — 이를 구현하고(`ARCH-0702`), `CodeServiceGenerationExecutor`(CRUD Pipeline의
> 유일한 WRITE 어댑터)를 공용 Port 위로 전환했다(`ARCH-0716`). `outputPath`가 허용된 위치인지 검증은
> `CodeService.validateOutputRoot`(기존 allowlist 검증 로직 추출)로 그대로 유지해 보안 경계가
> 빠지지 않게 했다. 전환 도중 "렌더 실패와 저장 실패가 섞여도 레이어 순서대로 누적된다"는 기존
> 테스트 계약을 배치 처리가 깨뜨리는 실제 회귀를 잡아 원본 레이어 순서를 보존하도록 재조립하는
> 방식으로 고쳤다(`CodeServiceGenerationExecutorTest`, 기존 `CrudGenerationApplicationServiceTest`/
> `CrudOrchestrationServiceTest`/`CrudOrchestrationProcessorOrderTest` 회귀 없이 통과).
>
> Board/Master-detail(`ARCH-0717/0718`)은 조사 결과 CRUD와 다른 이유로 계속 보류한다 — 모델이 안
> 맞아서가 아니라 개별 호출부의 성격이 배치 전환의 이점이 없거나(단일 파일 write 4곳:
> `MasterDetailMainControllerProcessor`, `MasterDetailServletScanProcessor`), 현재 모델이 지원하지
> 않는 바이너리 콘텐츠를 다루거나(`ClasspathAssetCopier.saveGeneratedBinary`, `byte[]` — `FileChange`는
> `String content`만 지원), 파일별 skip/preserve 판정이 렌더와 즉시 얽혀 있어 CRUD처럼 "먼저 다
> 모으고 배치 적용"으로 단순 재구성할 수 없기(`ThymeleafLayoutGenerationService`) 때문이다. 각각 별도
> 스코프의 작업(바이너리 콘텐츠 지원, skip/preserve 로직 분리)이 선행돼야 한다.
>
> `CodeSaverTool`/`ToolApiController`(단발성 MCP Tool·REST 진입점)는 재검토 결과 전환하지 않는
> 것으로 확정한다(`ARCH-0719`) — "생성 계획"이라는 개념 자체가 없는 완전히 독립적인 단일 파일 저장
> 호출이라, `ProjectChangeSet`으로 옮기면 매 호출마다 그 파일의 부모 디렉터리를 임시 project root로
> 취급해야 해 이 계약이 주는 이점(단일 root 기준 drift 검사·배치 원자성)이 전혀 없다.
