# eGovFrame MCP 소스 일관성 규제 방안

작성일: 2026-05-20

---

## 1. 문제 정의

동일한 타입의 소스를 반복 요청할 때 매번 다른 결과가 생성되는 문제.

### 현재 소스 생성 흐름

```
getCodeTemplate(layer)              ← 서버: 고정 템플릿 반환
      ↓
  Claude (LLM) 가 플레이스홀더 치환   ← ❌ 비결정적 구간
      ↓
saveGeneratedCode(filePath, code)   ← 서버: 저장
```

### 불일치 발생 원인

| 원인 | 상세 |
|---|---|
| LLM 확률적 특성 | temperature > 0이면 같은 입력도 다른 출력 가능 |
| 자유 해석 | 템플릿 외 메서드·주석·import를 Claude가 임의 추가 |
| 컨텍스트 의존 | 이전 대화 내용이 생성 결과에 영향 |
| 플레이스홀더 오치환 | `{{DOMAIN_KR}}`을 Claude가 다르게 해석할 수 있음 |

---

## 2. 현재 방어 수단 현황

| 수단 | 현재 상태 | 한계 |
|---|---|---|
| `CodeTemplateTool` | 고정 템플릿 제공 | LLM이 임의 변형 가능 |
| `CodeValidatorService` | 키워드 존재 여부 검사 | 구조·순서·내용 변형 검출 불가 |
| `buildFullCrudPrompt()` | 플레이스홀더 값 자동 생성 | 여전히 LLM이 치환 |
| `GenerationHistoryTool` | 이력 저장 | 비교·차단 기능 없음 |

---

## 3. 방안 비교

### 방안 A — 서버 사이드 직접 치환 Tool 추가 ★ 핵심 권장

LLM이 치환하는 구간을 **서버로 이동** — 근본적 해결책.

#### 변경 흐름

```
buildFullCrudPrompt()          ← 모든 플레이스홀더 값 생성 (이미 구현)
      ↓
generateSource(layer, values)  ← 서버에서 직접 String.replace() 치환 (신규)
      ↓
saveGeneratedCode()            ← 저장 (이미 구현)
```

#### 구현 위치

- `CodeService.generateSource(layer, Map<String, String> values)` 신규 추가
- `CodeSaverTool` 또는 신규 Tool에 `@Tool generateSource()` 추가

#### 예시

```java
// CodeService
public String generateSource(String layer, Map<String, String> values) {
    String template = codeTemplateTool.getCodeTemplate(layer);
    for (Map.Entry<String, String> entry : values.entrySet()) {
        template = template.replace("{{" + entry.getKey() + "}}", entry.getValue());
    }
    return template;
}
```

#### 평가

| 항목 | 내용 |
|---|---|
| 일관성 보장 | 동일 파라미터 → **100% 동일 소스 보장** |
| LLM 개입 | 없음 |
| 기존 재사용 | `CodeTemplateTool` 템플릿 그대로 사용 |
| 구현 난이도 | 중간 |

---

### 방안 B — CodeValidatorService 검증 규칙 강화

현재 키워드 단순 포함 검사 → **정규식 기반 구조 검사** 추가.

#### 현재 vs 강화 비교

```java
// 현재: 단순 포함 여부
content.contains("@Controller")

// 강화: 선언 위치·구조까지 검사
Pattern.compile("@Controller\\s+public class \\w+Controller")
       .matcher(content).find()
```

#### 추가 검사 항목

| 파일 | 추가 검사 규칙 |
|---|---|
| Controller | 클래스명 `Egov{Domain}Controller` 패턴 |
| ServiceImpl | `EgovAbstractServiceImpl` 상속 위치 |
| Mapper | `EgovAbstractMapper` 상속 + 메서드 시그니처 |
| VO | `pageIndex`, `searchCondition`, `searchKeyword` 필드 존재 |
| MapperXml | `selectList`, `selectTotCnt`, `insert`, `update`, `delete` ID 패턴 |

#### 평가

| 항목 | 내용 |
|---|---|
| 일관성 보장 | 사후 탐지만 가능 — 완전 보장 불가 |
| 기존 구조 변경 | 최소 (`CodeValidatorService` 내부만) |
| 구현 난이도 | 낮음 |

### 방안 C — 생성 이력 기반 중복 차단

동일 `tableName + layer` 재생성 요청 시 이전 결과와 비교·경고.

#### 구현 예시

```java
// GenerationHistoryService 확장
public String checkDuplicateGeneration(String tableName, String layer) {
    // AI_GENERATION_HISTORY에서 동일 테이블+레이어 이력 조회
    // 존재하면: "이미 생성된 이력 있음 + 이전 생성 경로" 반환
    // 없으면: "신규 생성 진행" 반환
}
```

#### 평가

| 항목 | 내용 |
|---|---|
| 일관성 보장 | 재생성 경고 수준 — 완전 보장 불가 |
| 활용 | 불필요한 재생성 방지, 이력 추적 |
| 구현 난이도 | 낮음 |

### 방안 D — @Tool description 강화 + temperature 제어

`getCodeTemplate()` Tool description에 엄격한 제약 추가.

#### @Tool description 변경

```
반환된 템플릿의 {{플레이스홀더}}만 치환하세요.
임의 메서드 추가, 주석 변경, import 변경 절대 금지.
템플릿 구조를 그대로 유지하세요.
플레이스홀더가 없는 줄은 한 글자도 변경하지 마세요.
```

#### application.yaml temperature 설정

```yaml
# 변경 전
ollama:
  chat:
    options:
      temperature: 0.3

# 변경 후 (소스 생성 요청 시)
ollama:
  chat:
    options:
      temperature: 0.0   # 완전 결정적 출력
```

#### 평가

| 항목 | 내용 |
|---|---|
| 일관성 보장 | 개선되나 LLM 특성상 완전 보장 불가 |
| 코드 변경 | 없음 — 즉시 적용 가능 |
| 구현 난이도 | 매우 낮음 |

## 4. 최종 권장 방안 — A + B + D 조합 (단계적 구현)

### 구현 로드맵

```
[즉시] 방안 D
  - @Tool description 강화
  - temperature 0.0 설정
  - 코드 변경 없이 즉시 적용
  - LLM 변형 억제 효과

      ↓

[단기] 방안 B
  - CodeValidatorService 정규식 기반 구조 검사 강화
  - 생성 후 이상 소스 탐지 게이트 역할
  - CodeValidatorService 내부만 변경

      ↓

[중기] 방안 A
  - CodeService.generateSource() 서버 사이드 치환 구현
  - LLM 치환 구간 완전 제거
  - 근본적 일관성 보장
```

### 최종 목표 흐름

```
buildFullCrudPrompt()
  → 플레이스홀더 값 Map 생성 (서버)
        ↓
generateSource(layer, valuesJson)
  → 서버에서 직접 String.replace() 치환
  → 완성 소스 반환 (신규 Tool)
        ↓
saveGeneratedCode()
  → 저장 (서버)
        ↓
validateGeneratedCodeDirectory()
  → 정규식 기반 구조 검사 (강화)
        ↓
checkProjectHealth()
  → 도메인 완성도 최종 점검
```

| 방안 | 일관성 보장 | 구현 난이도 | 적용 시점 |
|---|---|---|---|
| D — description + temperature | 70% | 매우 낮음 | 즉시 |
| B — 검증 규칙 강화 | 사후 탐지 | 낮음 | 단기 |
| C — 이력 기반 중복 차단 | 재생성 경고 | 낮음 | 단기 |
| A — 서버 사이드 치환 | **100%** | 중간 | 중기 |
| **A + B + D 조합** | **100% + 사후 검증** | 단계적 | 단계적 |
