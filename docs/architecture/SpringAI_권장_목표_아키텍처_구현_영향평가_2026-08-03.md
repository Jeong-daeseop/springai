# SpringAI 권장 목표 아키텍처 구현 영향평가

> 작성일: 2026-08-03  
> 대상 프로젝트: `springai`  
> 기준 문서: [SpringAI 프로젝트 전체 아키텍처 재분석](./SpringAI_프로젝트_전체_아키텍처_재분석_2026-08-03.md)  
> 평가 범위: 기준 문서 §17 구조적 위험과 개선 우선순위 12개 항목  
> 목표 구조: 기준 문서 §18 권장 목표 아키텍처  
> 상태: 구현 전 영향평가

## 1. 목적

이 문서는 현재 모듈형 모놀리스의 구조적 위험을 제거하면서 다음 목표 구조로 점진적으로 전환할 때의
영향을 평가한다.

```text
MCP / REST / Web Adapter
            ↓
Application Core
  ├─ Generation
  ├─ Design Specification
  ├─ Figma
  ├─ Thymeleaf Conversion
  └─ RAG / Chat
            ↓
공통 Port
  ├─ Operation Repository Port
  ├─ Artifact Store Port
  ├─ Approved Project Write Port
  └─ LLM / Vision Port
            ↓
Infrastructure Adapter
  ├─ MySQL + Migration
  ├─ Redis Vector / Memory / Operation
  ├─ Atomic File / Artifact
  └─ Figma / OpenAI / Ollama / Extractor
```

핵심 목적은 기능을 곧바로 별도 서비스로 분리하는 것이 아니다. 먼저 한 JVM 안에서 인증, 상태,
Artifact, 프로젝트 쓰기, 외부 연동의 경계를 Port로 명확하게 만들고 테스트로 의존 방향을 고정하는
것이다.

## 2. 종합 판정

전체 변경 영향도는 **매우 높음**이다. 이유는 Java 클래스 이동 자체보다 다음 운영 계약이 동시에
영향을 받기 때문이다.

- 97개 MCP 공개 메서드와 REST 요청·응답 계약
- Figma·Thymeleaf Operation 상태 전이와 승인 hash
- MySQL의 애플리케이션 관리 테이블과 기존 데이터
- 생성 프로젝트에 대한 파일 쓰기·backup·rollback 의미
- Figma Bundle, Web Capture, Design Artifact의 저장 방식
- Spring profile, bootJar 리소스 로딩, 외부 시스템 장애 처리
- 전체 테스트와 `-Pci` 테스트 범위

단, 목표 구조는 현재 코드를 전면 재작성하지 않고도 달성할 수 있다. 기존 Service를 새 Port 뒤에
Adapter로 먼저 감싸고, 소비자를 한 경로씩 전환한 뒤 구형 경로를 제거하는 방식이 가장 안전하다.

## 3. 영향도 평가 기준

| 등급 | 판단 기준 |
|---|---|
| 매우 높음 | 인증 우회, 데이터 손실, 잘못된 승인, 외부 계약 파괴 가능성이 있음 |
| 높음 | 여러 기능과 저장소를 함께 바꾸며 회귀 시 운영 기능이 중단됨 |
| 중간 | 단일 기능군 또는 운영 설정에 영향, 명확한 fallback이 있음 |
| 낮음 | 문서·테스트·정적 구조 중심이며 런타임 동작 변화가 제한됨 |

평가 관점은 보안, 데이터, 외부 계약, 파일 시스템, 가용성, 성능, 배포, 테스트, 운영 복잡도다.

## 5. P0 위험 영향평가

### 5.1 `RISK-01` MCP 인증 경계 불균일

현재 영향 근거:

- `SecurityConfig`는 `/mcp/**`를 `permitAll`로 처리한다.
- Figma와 Thymeleaf 일부 Tool만 메서드 내부 shared secret 검사를 수행한다.
- 조회·DB 접근·파일 접근 Tool마다 인증 강도가 다르다.

실패 시나리오:

- 서버 bind 또는 reverse proxy 설정 오류로 MCP 경로가 외부에 노출된다.
- 인증 없는 호출자가 DB 조회, 문서 인덱싱 또는 파일 관련 Tool을 실행한다.
- Tool마다 다른 거부 응답을 사용해 감사와 침해 탐지가 어려워진다.

변경 영향:

| 영역 | 영향 |
|---|---|
| MCP 계약 | 인증 metadata/header 추가 시 기존 Client 설정 변경 필요 |
| Security | Filter, interceptor, Tool risk policy와 예외 응답 표준화 필요 |
| 운영 | secret 회전, local-only 정책, reverse proxy 설정 필요 |
| 테스트 | 모든 MCP Tool의 인증 전·후 계약 테스트 필요 |

목표 구조 대응:

- MCP Adapter에서 인증을 끝낸 뒤 Application Core를 호출한다.
- Core Service는 shared secret 문자열을 받지 않고 인증된 `ActorContext`와 권한만 받는다.
- 위험 Tool 정책은 `ToolAuthorizationPolicy` 한곳에서 관리한다.

전환 위험 완화:

1. audit-only 모드에서 위험 Tool 분류 누락을 탐지한다.
2. 기존 shared secret과 공통 인증을 짧은 기간 함께 허용한다.
3. Client 설정 배포 후 메서드 내부 secret을 제거한다.

### 5.2 `RISK-02` Prototype Bridge의 거짓 성공

현재 영향 근거:

- `FigmaThymeleafBridgeTool.validateThymeleafDesignParity`가 실제 Figma 조회 없이 `VERIFIED`를 반환한다.
- `syncDesignTokensToCss`가 공통 안전 경계를 거치지 않고 경로를 직접 읽는다.

실패 시나리오:

- 실제 디자인 parity가 검증되지 않았는데 후속 승인 단계가 성공으로 판단한다.
- 임의 경로 입력으로 허용된 프로젝트 범위 밖의 파일 내용이 노출된다.

목표 구조 대응:

- Prototype Adapter를 MCP 등록에서 제거하거나 명시적인 `UNSUPPORTED` 결과만 반환한다.
- parity는 Figma Core와 Thymeleaf Core가 생산한 승인 Artifact를 `DesignParityValidationUseCase`에서 비교한다.
- 파일 입력은 `ArtifactRef` 또는 `ApprovedProjectPath`만 사용한다.

영향도는 매우 높지만 구현 난도는 상대적으로 낮다. 따라서 다른 리팩터링보다 먼저 공개 면적을
줄이는 것이 적절하다.

### 5.3 `RISK-03` Thymeleaf Operation 메모리 전용

현재 영향 근거:

- `ThymeleafProjectWorkflowService`가 `ConcurrentHashMap`에 snapshot을 보관한다.
- 재시작 후 승인 상태와 report를 복구할 수 없다.
- 다중 인스턴스에서 동일 operation의 Apply를 직렬화할 수 없다.

실패 시나리오:

- 승인 직후 서버가 재시작되어 Apply 또는 rollback 근거가 사라진다.
- 두 인스턴스가 동일 projectRoot에 동시에 파일을 적용한다.
- 메모리 증가와 만료되지 않는 Operation으로 장기 실행 안정성이 저하된다.

목표 구조 대응:

- Core에는 `OperationRepositoryPort`, `OperationLockPort`, `OperationEventPort`를 둔다.
- MySQL Adapter는 불변 revision과 optimistic lock을 저장한다.
- Redis Adapter는 짧은 수명의 distributed lock 또는 조회 cache만 담당한다.
- 상태 전이는 공통 `OperationStatePolicy`가 검증한다.

데이터 영향:

- 신규 Operation/Revision/Event 테이블 또는 기존 Figma 테이블 일반화가 필요하다.
- 기존 메모리 Operation은 이관할 수 없으므로 배포 전에 진행 중 작업을 종료해야 한다.

### 5.4 `RISK-04` Bound View 생성 경로 공백

현재 영향 근거:

- 기존 legacy assembler/renderer 제거 이후 JSP·Controller·VO evidence와 생성 View를 완전히 결합하는
  새 경로가 부족하다.
- 정적 Skeleton만으로는 `th:*`, route, CSRF, validation의 업무 근거를 보장할 수 없다.

실패 시나리오:

- 존재하지 않는 model attribute 또는 route를 생성한다.
- 원본 JSP의 조건·반복·권한 표현이 누락된다.
- 디자인 규칙이 업무 binding을 덮어써 화면은 보이지만 기능이 잘못된다.

목표 구조 대응:

```text
Legacy Source Analyzer
        ↓
ThymeleafBindingContract
        ↓
ScreenSpecification + Design Rules
        ↓
Skeleton Planner
        ↓
Binding Composer
        ↓
Provenance / Render / Build Gate
```

영향 범위는 Thymeleaf Core, 계약 Schema, Fixture, Template, Validation Gate다. Figma Core는 직접
참조하지 않고 승인된 `ScreenSpecification`과 `ArtifactRef`만 전달해야 한다.

## 6. P1 위험 영향평가

### 6.1 `RISK-05` 두 파일 적용 의미 공존

현재 일반 Generation Pipeline은 파일별 best-effort이고 Thymeleaf Workflow는 staging·backup·보상
rollback을 사용한다. 같은 프로젝트 생성 기능인데 호출 경로에 따라 원자성과 실패 의미가 다르다.

목표 구조에서는 다음 Port로 수렴한다.

```text
ApprovedProjectWritePort
  ├─ preview(ChangeSet)
  ├─ approve(previewHash)
  ├─ apply(operationId)
  ├─ rollback(operationId)
  └─ validate(operationId)
```

영향:

- Generation 결과를 즉시 저장하는 대신 `ProjectChangeSet`으로 반환해야 한다.
- 기존 MCP 응답과 파일 생성 timing이 바뀔 수 있다.
- 하위 호환을 위해 `BEST_EFFORT`와 `ATOMIC_APPROVED` 정책을 명시적으로 모델링해야 한다.
- 장기적으로 자동 생성 기본값을 승인 기반 원자 적용으로 변경해야 한다.

### 6.2 `RISK-06` DB migration 부재

각 Repository의 `@PostConstruct CREATE TABLE IF NOT EXISTS`는 schema version과 적용 순서를 보장하지
않는다. Operation과 Artifact 공통 테이블을 추가하기 전에 Flyway 또는 Liquibase 기준선을 먼저
도입해야 한다.

영향:

- 기존 운영 DB baseline version을 안전하게 지정해야 한다.
- Repository DDL 제거는 migration 적용 확인 후 단계적으로 수행해야 한다.
- CI에 빈 DB migration과 기존 schema upgrade 검증이 필요하다.
- 실패 시 애플리케이션 기동을 차단해야 한다.

### 6.3 `RISK-07` 운영 리소스 경로 source-relative

`file:src/main/resources/...` 경로는 IDE 실행에는 적합하지만 working directory가 다른 bootJar 실행에서
깨질 수 있다.

목표 구조 대응:

- `dev` profile은 선택적으로 file resource와 cache-off를 사용한다.
- `prod` profile은 `classpath:/templates/`, `classpath:/static/`을 사용한다.
- 외부 교체가 필요한 template만 별도 명시적 directory property로 분리한다.

영향은 설정과 배포 테스트 중심이며 도메인 코드 영향은 낮다.

### 6.4 `RISK-08` 단일 프로세스 장애 반경

MySQL, Redis, Ollama, OpenAI, Figma, Extractor 호출이 한 JVM에 모여 있어 timeout 또는 thread 고갈이
전체 입력 채널에 전파될 수 있다.

목표 구조 대응:

- 외부 시스템마다 Port와 timeout, bulkhead, circuit breaker, health indicator를 둔다.
- 동기 요청과 장시간 Capture/Indexing 작업을 다른 executor로 격리한다.
- 우선 한 JVM에서 격리하고 실제 부하 지표가 분리 기준을 넘을 때 Worker로 추출한다.

즉시 마이크로서비스 분리는 배포·트랜잭션 복잡도를 불필요하게 늘리므로 권장하지 않는다.

### 6.5 `RISK-09` 상태와 Artifact 이중 저장

MySQL Operation JSON과 파일 metadata가 별도로 변경되면 orphan 파일 또는 존재하지 않는 Artifact 참조가
발생할 수 있다.

목표 구조 대응:

- `ArtifactStorePort`와 `ArtifactCatalogRepositoryPort`를 분리한다.
- 파일은 immutable content hash로 저장하고 DB catalog가 수명주기를 관리한다.
- DB commit 이후 파일 정리·후속 처리는 outbox/reconciler로 수행한다.
- operation revision은 `artifactId`만 참조한다.

이 변경은 Figma Bundle, Web Capture, `.figpack`, Thymeleaf Preview, 생성 보고서에 공통으로 영향을 준다.

## 7. P2 위험 영향평가

### 7.1 `RISK-10` 컴파일 수준 module 경계 없음

575개 Java 파일이 단일 Gradle module에 있고 패키지 규칙만으로 결합을 제어한다.

권장 전환:

1. 패키지 의존 규칙을 ArchUnit으로 먼저 고정한다.
2. Application Port와 Infrastructure 구현을 분리한다.
3. 순환 의존을 제거한다.
4. 안정된 경계만 Gradle subproject로 이동한다.

초기부터 multi-module로 이동하면 package relocation과 Bean scan 회귀가 동시에 발생하므로 영향이 너무
크다. 논리 경계 검증을 먼저 수행해야 한다.

### 7.2 `RISK-11` 관측성 부족

현재 파일 로그만으로는 하나의 MCP 호출이 Operation, Artifact, Figma Plugin 또는 Project Apply까지
어떻게 진행됐는지 연결하기 어렵다.

추가 영향:

- `operationId`, `correlationId`, `actorId`, `artifactId`를 공통 context로 전달해야 한다.
- Micrometer metric label은 fileKey, 사용자 입력 등 고 cardinality 값을 포함하지 않아야 한다.
- health는 단순 연결 여부와 기능 준비 상태를 구분해야 한다.

### 7.3 `RISK-12` 문서와 AGENTS 수치 drift

Tool 객체·메서드 수 같은 수동 수치는 구조 변경 때 빠르게 오래된다.

목표 구조 대응:

- MCP snapshot, package inventory, schema 목록을 기계 생성 가능한 source of truth로 사용한다.
- 문서에는 생성 결과 링크 또는 검증 시점과 commit을 기록한다.
- CI는 문서 내 핵심 수치와 snapshot 불일치를 탐지한다.

## 8. 교차 영향과 결합 위험

| 결합 | 위험 | 통제 방법 |
|---|---|---|
| 인증 + Tool 분리 | 신규 Adapter가 정책 등록에서 빠질 수 있음 | deny-by-default와 Tool inventory test |
| Operation + Migration | 코드가 schema보다 먼저 배포될 수 있음 | expand→migrate→switch→contract 순서 |
| Artifact + Operation | DB commit과 파일 이동 사이 실패 | immutable staging, outbox, reconciler |
| Project Write + Generation | 기존 즉시 생성 계약이 깨질 수 있음 | compatibility mode와 golden fixture |
| Bound View + Design | 디자인 규칙이 업무 binding을 변경할 수 있음 | 업무 계약 우선순위와 provenance Gate |
| Bulkhead + SSE | timeout 정책이 정상 stream을 끊을 수 있음 | 연결/첫 token/idle timeout 분리 |
| Multi-module + Spring Bean | component scan과 conditional bean 누락 | context test와 ArchUnit 단계 선행 |

## 9. 데이터 및 배포 전환 원칙

### 9.1 데이터베이스

- 기존 테이블은 바로 이름을 변경하지 않는다.
- migration baseline 후 공통 테이블을 추가한다.
- 기존 Figma Operation은 Adapter를 통해 유지하고 공통 Port를 먼저 적용한다.
- 이중 쓰기가 필요하면 기간과 종료 조건을 명시한다.
- migration은 expand→backfill→switch read→switch write→contract 순서를 따른다.

### 9.2 파일 시스템

- 사용자 프로젝트 원본을 migration 대상으로 취급하지 않는다.
- 모든 신규 쓰기는 project root, relative path, source hash가 포함된 `ProjectChangeSet`을 거친다.
- backup 삭제는 검증 완료와 보존 기간 경과 후 별도 cleanup에서 수행한다.

### 9.3 배포

- P0 공개 면적 축소는 독립 배포 가능해야 한다.
- Operation/Artifact schema는 application switch보다 먼저 배포한다.
- profile 전환은 bootJar smoke test와 함께 적용한다.
- Worker 분리는 metric으로 필요성이 입증되기 전에는 수행하지 않는다.

## 11. 성능과 운영 영향

- Operation 영속화는 DB write를 늘리지만 재시작 복구와 감사 가능성이 더 중요하다.
- 모든 중간 파일을 Artifact로 저장하면 용량이 증가하므로 retention과 deduplication이 필요하다.
- distributed lock은 projectRoot 단위로 최소화해 병렬 작업을 불필요하게 직렬화하지 않는다.
- 외부 호출 bulkhead는 장애 전파를 줄이지만 executor와 queue 크기 조정이 필요하다.
- metric label에 operationId를 사용하지 않고 trace/log field로만 기록한다.

## 12. 구현하지 않을 경우의 잔여 위험

| 위험 | 예상 결과 |
|---|---|
| P0 미조치 | 인증 우회, 임의 파일 접근, 거짓 승인, 재시작 시 승인 작업 소실 가능 |
| P1 미조치 | 부분 파일 적용, schema drift, bootJar UI 실패, 외부 장애 전파, orphan Artifact 누적 |
| P2 미조치 | 결합도 증가, 장애 분석 지연, 문서 기반 운영 판단 오류 |

## 13. 최종 권고

구현은 다음 순서를 지켜야 한다.

1. 공개 면적과 거짓 성공을 먼저 차단한다.
2. Migration, Operation, Artifact 공통 기반을 만든다.
3. Bound View와 Project Write를 공통 Port에 연결한다.
4. 운영 profile, 장애 격리, 관측성을 추가한다.
5. 의존 경계를 검증한 뒤에만 multi-module 또는 Worker 분리를 검토한다.

따라서 목표 아키텍처의 첫 번째 성공 기준은 “모듈 수”가 아니라 **인증된 요청이 승인된 계약과
영속 Operation을 거쳐 불변 Artifact를 만들고, 검증된 Project Write Port로만 변경을 적용하는가**다.
