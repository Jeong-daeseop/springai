#### `initializeProject()` 구현 구조 분석

**입력 파라미터 8개 → Spec 레코드 → 4단계 파일 생성**

```
initializeProject(8 params)
    ├─ isLatest 플래그 계산 ("5.0" / "latest" / "5.*" → true)
    ├─ Spec 레코드 생성 (isBoot, isLatest, groupId, artifactId, packageName, buildTool)
    ├─ createDirectories()   — 디렉터리 골격
    ├─ createBuildFile()     — build.gradle / pom.xml
    ├─ createBootFiles() 또는 createWarFiles()
    └─ buildResult()         — 생성 목록·오류·다음 단계 안내 반환
```

#### eGovFrame 4.3 → 5.0 주요 설계 포인트 코드 대조 검토

**검토 대상 포인트 (사전 정의):**
1. eGovFrame 5.x Maven Artifact 명명 규칙 변경 대응
2. Spring 6 Multipart 처리 방식 변경 대응
3. Jakarta EE 전환 대응 (web.xml·servlet API·validation API 등 namespace 자동 분기)
4. Runtime Compatibility 분기 처리 (Tomcat 9/javax ↔ Tomcat 10+/jakarta, Spring 5.x/6.x 의존성)

---

**포인트 1 — eGovFrame Artifact 명명 규칙 변경 ✅ 적합**

코드와 정확히 일치. eGovFrame 고유 변경으로 Spring 공식 마이그레이션 가이드에 없어 실무자가 놓치기 쉬운 지점.

```java
// WAR pom.xml / build.gradle — 4개 모듈 전부 분기
String fdlCmmnId = s.isLatest ? "egovframe-rte-fdl-cmmn"      // 5.0: 하이픈
                              : "org.egovframe.rte.fdl.cmmn"; // 4.3: 점
```

빌드 단계에서 즉시 실패(`Could not resolve`)하므로 독립 포인트로 적합.

---

**포인트 2 — Spring 6 Multipart 처리 방식 변경 ✅ 적합 (단, 설명 보완 필요)**

코드와 일치. 단 "Servlet 표준 multipart-config 설정 적용" 표현만으로는 web.xml 한 곳만 수정하는 것처럼 읽힘. 실제로는 **2개 파일이 쌍으로 변경**되어야 한다는 점이 핵심 복잡도.

```java
// dispatcher-servlet.xml — 리졸버 클래스 분기
String multipartBean = isLatest ? "StandardServletMultipartResolver"
                                : "CommonsMultipartResolver";

// web.xml — isLatest 일 때만 <multipart-config> 블록 추가
String multipartConfig = isLatest ? "<multipart-config>...</multipart-config>" : "";
```

> ⚠️ 보완 필요: "dispatcher-servlet.xml + web.xml 2개 파일 동시 수정"을 명시해야 정확.

---

**포인트 3 — Jakarta EE 전환 ⚠️ 범위 과장**

web.xml namespace + servlet-api 의존성은 처리되었으나, "validation API 등 namespace 자동 분기 처리"는 코드에 없음.

| 항목 | 코드 처리 여부 |
|---|---|
| web.xml xmlns (`javax` → `jakarta`) | ✅ 처리 |
| servlet-api 의존성 (`javax.servlet-api` → `jakarta.servlet-api`) | ✅ 처리 |
| validation API (`javax.validation` → `jakarta.validation`) | ❌ 미처리 (의존성 자체 미포함) |
| Java 소스 import (`import javax.servlet.*` → `import jakarta.servlet.*`) | ❌ 미처리 (생성되는 Controller 템플릿 등 미분기) |

> ❌ Gap: "자동 분기 처리"라는 표현이 Java import 미처리 Gap을 가림. 처리 범위를 web.xml·servlet-api 의존성으로 한정하고 Java import를 별도 이슈로 명시해야 함.

---

**포인트 4 — Runtime Compatibility 분기 ❌ 독립 포인트 불가**

Tomcat 버전을 직접 감지하거나 분기하는 로직이 코드에 없음. 실제 구현은 `isLatest` 단일 플래그 하나가 포인트 1·2·3 전부를 제어.

```java
// 모든 분기의 실제 제어 메커니즘
boolean isLatest = "latest".equalsIgnoreCase(egovVersion)
                || "5.0".equalsIgnoreCase(egovVersion)
                || (egovVersion != null && egovVersion.startsWith("5."));
```

Tomcat 호환성은 egovVersion 선택의 **결과**이며, "Spring 5.x/6.x 의존성 자동 분기"는 포인트 1·2·3에서 이미 설명된 내용의 반복. 포인트 4는 migration 포인트가 아닌 **구현 메커니즘(isLatest 플래그)** 설명임.

---

**종합 판정**

| 포인트 | 판정 | 비고 |
|---|---|---|
| 1. artifact ID 명명 규칙 | ✅ 적합 | 코드 일치, eGovFrame 고유 포인트 |
| 2. Multipart 처리 방식 | ✅ 적합 (보완) | 2파일 동시 수정 명시 필요 |
| 3. Jakarta EE 전환 | ⚠️ 범위 과장 | validation·Java import 미처리, "자동 분기" 표현이 Gap 은폐 |
| 4. Runtime Compatibility | ❌ 독립 불가 | Tomcat 직접 감지 없음, isLatest 플래그 설명에 해당 |

**수정 방향**: 포인트 4 제거, 포인트 3 처리 범위를 web.xml namespace + servlet-api 의존성으로 한정, Java import 미처리를 별도 제약 사항으로 명시

## 4. CRUD 자동 생성 플로우

### 단일 테이블 (기존)

```
사용자: "COMTNEMPLYRINFO 테이블 CRUD 만들어줘"
    ↓
buildFullCrudPrompt()
  - DB에서 컬럼·PK·타입 자동 조회
  - 플레이스홀더 자동 생성
  - 공통코드 컬럼 자동 탐지 및 매핑
  - Step 1~10 생성 지시 조합
    ↓
generateSource(layer, valuesJson) × 10  +  saveGeneratedCode() × 10
  Step  1~10: vo / mapper / mapperXml / service / serviceImpl
              / controller / jspList / jspDetail / jspRegist / jspUpdt
    ↓
validateGeneratedCodeDirectory() → saveGenerationHistory() → checkProjectHealth()

결과: 10개 파일 end-to-end 자동 생성·검증·이력 저장 완료
```

### 마스터-디테일 (P2 신규)

```
사용자: "COMTNEMPLYRINFO + COMTNEMPLYRATTRBINFO 마스터-디테일 화면 만들어줘"
    ↓
getTableRelations("com", "COMTNEMPLYRINFO")
  - 자식 테이블(COMTNEMPLYRATTRBINFO) 탐지
  - FK 컬럼(EMPLYR_ID) 확인
    ↓
buildMasterDetailPrompt(database, masterTable, detailTable, ...)
  - 마스터/디테일 스키마 자동 조회
  - FK 컬럼 자동 탐지
  - 12개 파일 생성 지시 + Controller 패턴 + JSP 그리드 탭 패턴 반환
    ↓
generateSource() + saveGeneratedCode() × 12
  마스터 VO, 디테일 VO, 마스터 Mapper, 디테일 Mapper,
  마스터 MapperXml (디테일 목록 쿼리 포함), 디테일 MapperXml,
  Service, ServiceImpl, Controller, jspList, jspDetail (그리드 탭), jspRegist
    ↓
validateGeneratedCodeDirectory() → saveGenerationHistory() → checkProjectHealth()
```

### JOIN SELECT (P2 신규)

```
사용자: "COMTNEMPLYRINFO 조회 시 공통코드명·부서명 JOIN 추가해줘"
    ↓
getTableRelations("com", "COMTNEMPLYRINFO")
  - 공통코드 JOIN 후보 컬럼 탐지
  - 부서 JOIN 후보 탐지
    ↓
buildJoinSelectPrompt("com", "COMTNEMPLYRINFO")
  - JOIN 후보 컬럼 → JOIN 절 자동 조합
  - VO 추가 필드 목록 (CodeNm, DeptNm 등)
  - SELECT + resultMap XML 초안 반환
    ↓
기존 VO / Mapper XML 수정 적용
```

### ProjectInitializr — 4.3 ↔ 5.0 동시 생성기 Gap 항목

> 상세 분석: `docs/ProjectInitializr_migration_구현검토.md`

**이미 구현된 항목 (오해 방지)**

| 항목 | 확인 근거 |
|---|---|
| Java 버전 분기 (11/17) | `JAVA_11`·`JAVA_17` 상수 + Gradle toolchain + Maven `<java.version>` |
| JSTL 의존성 분기 | 4.3: `javax.servlet:jstl:1.2` / 5.0: `jakarta.servlet.jsp.jstl-api:3.0.0` + `org.glassfish.web:jakarta.servlet.jsp.jstl:3.0.1` (구현체) |
| Logging framework 분기 | WAR → `log4j2.xml` / Boot → `logback-spring.xml` |
| Build tool 표준화 | maven-compiler-plugin `<release>` + Gradle toolchain Java 버전 연동 |
| MyBatis Boot starter 버전 | 2.3.2(4.3) / 3.0.3(5.0) 분기 완료 |

**즉시 구현 권장 (런타임 오류 유발)**

| 항목 | 위치 | 상태 | 비고 |
|---|---|---|---|
| javax → jakarta Java import | `CodeTemplateTool` CRUD 템플릿 | ✅ 영향 없음 확인 | Controller 템플릿이 `@ModelAttribute`/`ModelMap` 사용 — `javax.servlet` import 없음 |
| JSP validator taglib 제거 | `CodeTemplateTool` `jspRegistTemplate()` | ✅ 구현 완료 | `spring-modules-validation` 깨진 taglib URI 제거 |
| Validation API 의존성 추가 | `ProjectInitializrService` | ✅ 구현 완료 | WAR: `javax/jakarta.validation-api` 분기, Boot: `spring-boot-starter-validation` 추가 |

**단기 구현 권장 (표준 위반)**

| 항목 | 위치 | 상태 | 비고 |
|---|---|---|---|
| MyBatis WAR 버전 분기 | `ProjectInitializrService` | ✅ 구현 완료 | `MYBATIS_SPRING_2=2.1.2`(4.3) / `MYBATIS_SPRING_3=3.0.3`(5.0) 상수 추가, warPomXml·warBuildGradle 분기 적용 |
| `buildResult()` Security 안내 | `ProjectInitializrService` | ✅ 구현 완료 | 다음 단계 2번에 `getSecurityTemplate()` 호출 안내 추가 (projectType·egovVersion 조합으로 권장 securityType 자동 선택) |

**중기 검토 (아키텍처 개선)**

| 항목 | 내용 | 상태 |
|---|---|---|
| Capability Matrix 기반 설계 | `isLatest` 단일 boolean → `supportsJakarta()` · `supportsSpring6()` 등 독립 메서드 분리. eGovFrame 5.1·5.2 이후 버전 확장성 확보 | ✅ 구현 완료 |

**핵심 구조적 이슈**

`initializeProject()`와 CRUD 소스 생성(`CodeTemplateTool`)이 `egovVersion`을 공유하지 않아,
5.0으로 생성한 프로젝트에도 CRUD 소스에 `javax` import가 삽입되는 불일치 발생.
근본 해결책: `GenerationHistory` 또는 세션 컨텍스트에 `egovVersion`을 저장하고
`CodeTemplateTool`이 참조하는 구조 필요.
