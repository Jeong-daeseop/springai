14. Thymeleaf 마이그레이션 승인 워크플로우 — CRUD 소스 생성과의 승인 단계 비교 신규 반영

13번에서 최다 사용 테이블로 드러난 AI_THYMELEAF_PROJECT_OPERATION을 실제로 쓰는 주체입니다. 레거시 JSP 화면을 Thymeleaf로 변환해 덮어쓰는, 위험도가 다른 별도 승인 상태기계이며, 2번 다이어그램의 2.2절(CRUD 소스 생성 경로)과는 한 번도 서로의 상위 서비스가 되지 않지만 파일 쓰기 계층(ApprovedProjectWritePort)은 설계 시점부터 공유하도록 되어 있습니다.

핵심 결론

CRUD 소스 생성과 Thymeleaf 마이그레이션은 동일한 파일 쓰기 Port를 공유하지만, 위험 모델과 승인 방식이 다르므로 실행기는 분리한다. CRUD 소스는 반복 재생성을 위해 Region 3-way(Base·Current·New) 비교 기반 자동 병합을 사용하고, Thymeleaf 마이그레이션은 레거시 화면 변환의 위험도를 고려해 Preview Hash·Source Revision·명시적 승인·Revalidate를 강제한다. 다만 2026-08-26부터 고위험으로 지정한 테이블에 한해 CRUD 소스 생성에도 조건부 승인 게이트(CrudGenerationApprovalPolicy, 2.2절)가 예외로 적용될 수 있다(기본값은 비활성).

통합 대상은 실행 알고리즘이 아니라 Generation Operation, Validation Evidence, Approval State, Conflict·Rollback Audit과 같은 제어 계층이며, 이 제어 계층은 14.1절에서 실제로 구현·커밋됐다 (GenerationControlPlaneService, 커밋 5ae8507). 다만 이는 위 CodeServiceGenerationExecutor의 "명시적 승인 단계 없음" 문제 자체를 고친 것이 아니다 — 14.1절의 Approval 값은 CRUD 소스 쪽이 여전히 AUTOMATED_OWNERSHIP_CHECK(사람 승인 없음)이므로, 승인 공백이 해소된 게 아니라 그 공백이 API로 관측 가능해졌을 뿐이다. ATOMIC_APPROVED는 승인 방식이 아니라 원자적 파일 쓰기 정책이므로, 사람 승인과 자동 3-way 판정 승인을 별도 계약으로 표현해야 한다.

같은 이유로 위 CodeServiceGenerationExecutor 박스는 여전히 주황(rest)+점선으로 남아 있다. 이 점선이 표시하는 건 기본 동작이지 예외 경로가 아니기 때문이다. CrudGenerationApprovalPolicy는 기본값이 꺼져 있는(approval-required-tables가 빈 목록) 선택적 게이트이므로, 운영자가 특정 테이블을 명시적으로 등록하지 않는 한 지금 이 순간에도 CRUD 소스 생성은 승인 없이 그대로 저장된다. 바뀐 건 "예외 경로 하나가 추가됐다"는 것이지 "기본 상태에 뚫려 있던 구멍이 막혔다"는 것이 아니다 — 그래서 박스 문구도 실선 전환 없이 "⚠ 기본은 승인 없음 — 고위험 테이블만 예외(2.2절)"로만 갱신했다. 만약 반대로 approval-required-for-all이 기본값 true였다면, 그때는 "기본적으로 항상 승인이 걸린다"는 뜻이므로 점선을 실선으로 바꾸는 게 맞았을 것이다.
