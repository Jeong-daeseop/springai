# 공통코드 및 파일 업로드 정책 입력 가이드

> 작성일: 2026-07-17  
> 관련 문서: `design-vision-remaining-external-actions-guide.md`  
> 대상: 업무 담당자, DB 담당자, 개발자, 인프라·보안 담당자

## 1. 개요

본 문서는 디자인 참조 기반 Board 생성에 필요한 공통코드와 파일 업로드 정책을 작성하는 방법을
설명합니다. 입력값은 생성기가 화면, Controller, Service, 저장소 및 검증 규칙을 일관되게 생성하기
위한 승인 계약으로 사용합니다.

값을 알 수 없는 항목은 임의로 정하지 않습니다. `미정`, `조회 필요`, `담당자 확인 필요` 중 하나로
표시하고 확인 주체를 함께 기록합니다. 비밀번호, API Key, S3 Secret Key와 같은 인증정보는 본 문서에
기록하지 않습니다.

## 2. 공통코드 작성 방법

### 2.1 전체 작성 예시

공지사항 등록 화면에서 공지 유형을 선택하는 경우의 예시는 다음과 같습니다.

```text
[공통코드]

업무명: 공지사항 관리
DB/schema: com
게시글 테이블: COMTNBBS
카테고리 컬럼: NOTICE_TYPE_CODE
원하는 카테고리 값:
- 일반공지: NORMAL
- 긴급공지: URGENT
- 시스템점검: MAINTENANCE
기존 CODE_ID: NOTICE_TYPE
필수 여부: 필수
기본값: NORMAL
```

### 2.2 업무명

공통코드를 사용하는 화면 또는 기능의 이름을 작성합니다.

```text
업무명: 공지사항 관리
```

다른 작성 예시는 다음과 같습니다.

```text
업무명: FAQ 관리
업무명: 자료실 관리
업무명: 사용자 문의 관리
업무명: 사업 신청 관리
```

화면명이 확정되지 않았다면 가칭임을 표시합니다.

```text
업무명: 게시판 관리(가칭)
```

### 2.3 DB/schema

대상 업무 테이블이 위치한 데이터베이스 또는 스키마 이름을 작성합니다.

```text
DB/schema: com
```

현재 연결된 데이터베이스는 다음 SQL로 확인할 수 있습니다.

```sql
SELECT DATABASE();
```

특정 테이블의 위치는 다음과 같이 확인합니다.

```sql
SELECT TABLE_SCHEMA, TABLE_NAME
FROM information_schema.TABLES
WHERE TABLE_NAME = 'COMTNBBS';
```

알 수 없는 경우에는 다음과 같이 작성합니다.

```text
DB/schema: 미정 — 현재 연결된 DB에서 조회 필요
```

### 2.4 게시글 테이블

사용자가 선택한 카테고리 코드가 실제로 저장되는 업무 테이블을 작성합니다.

```text
게시글 테이블: COMTNBBS
```

신규 테이블인 경우에는 예정된 테이블명을 작성합니다.

```text
게시글 테이블: TB_NOTICE — 신규 생성 예정
```

테이블이 확정되지 않았다면 다음과 같이 작성합니다.

```text
게시글 테이블: 미정 — 공지사항 업무 테이블 확인 필요
```

이 항목에는 `COMTCCMMNDETAILCODE`와 같은 공통코드 테이블을 작성하지 않습니다. 공통코드를 선택한
결과가 저장되는 게시글 또는 업무 테이블을 작성해야 합니다.

### 2.5 카테고리 컬럼

선택한 코드값을 저장할 실제 컬럼명을 작성합니다.

```text
카테고리 컬럼: NOTICE_TYPE_CODE
```

화면에는 `긴급공지`가 표시되더라도 DB에는 `URGENT`와 같은 코드값이 저장됩니다.

```text
화면 표시명: 긴급공지
DB 저장값: URGENT
```

기존 컬럼을 사용하면 실제 컬럼명을 기록하고, 컬럼을 추가해야 하면 그 사실을 명시합니다.

```text
카테고리 컬럼: BBS_TY_CODE
```

```text
카테고리 컬럼: NOTICE_TYPE_CODE — 신규 컬럼 추가 필요
```

### 2.6 원하는 카테고리 값

화면에 표시할 코드명과 DB에 저장할 코드값을 함께 작성합니다.

```text
원하는 카테고리 값:
- 일반공지: NORMAL
- 긴급공지: URGENT
- 시스템점검: MAINTENANCE
```

기관에서 숫자 코드를 사용한다면 기존 규칙에 맞춥니다.

```text
원하는 카테고리 값:
- 일반공지: 01
- 긴급공지: 02
- 시스템점검: 03
```

코드값을 아직 결정하지 않았다면 표시명만 작성하고 코드 제안을 요청할 수 있습니다.

```text
원하는 카테고리 값:
- 일반공지
- 긴급공지
- 시스템점검
코드값: 기존 공통코드 규칙에 맞춘 후보 제안 필요
```

기존 DB에 해당 코드가 있다면 신규 코드값을 임의로 만들지 않습니다. 기존 코드값, 사용 여부 및
표시 순서를 먼저 확인합니다.

### 2.7 기존 CODE_ID

eGovFrame 공통코드 그룹을 식별하는 `CODE_ID`를 작성합니다.

```text
기존 CODE_ID: NOTICE_TYPE
```

논리적인 관계는 다음과 같습니다.

```text
NOTICE_TYPE
├── NORMAL      → 일반공지
├── URGENT      → 긴급공지
└── MAINTENANCE → 시스템점검
```

기존 코드 그룹을 모르면 다음과 같이 작성합니다.

```text
기존 CODE_ID: 모름 — 유사 공통코드 그룹 조회 필요
```

일반적인 eGovFrame 공통코드 구조에서는 다음과 같은 읽기 전용 SQL로 후보를 확인할 수 있습니다.
실제 테이블명과 컬럼명은 대상 DB 구조에 맞게 조정해야 합니다.

```sql
SELECT CODE_ID, CODE, CODE_NM, USE_AT
FROM COMTCCMMNDETAILCODE
WHERE CODE_ID = 'NOTICE_TYPE'
ORDER BY CODE;
```

코드 그룹명을 기준으로 후보를 찾는 예시는 다음과 같습니다.

```sql
SELECT CODE_ID, CODE_ID_NM
FROM COMTCCMMNCODE
WHERE CODE_ID_NM LIKE '%공지%'
   OR CODE_ID_NM LIKE '%게시%'
ORDER BY CODE_ID;
```

신규 그룹이 필요한 경우에는 기존 그룹이 없다는 사실과 제안값을 분리해 작성합니다.

```text
기존 CODE_ID: 없음
신규 CODE_ID 제안: NOTICE_TYPE
```

신규 공통코드 INSERT는 업무 담당자와 DB 담당자의 승인을 받은 후 별도 절차로 수행합니다.

### 2.8 필수 여부

등록·수정 화면에서 반드시 선택해야 하는지 작성합니다.

```text
필수 여부: 필수
```

필수 항목은 다음 규칙을 함께 적용합니다.

- 화면의 `required` 속성
- 서버 입력값 검증
- 미선택 오류 메시지
- DB `NOT NULL` 적용 여부 검토

선택 항목은 미선택 값을 어떻게 저장할지도 작성합니다.

```text
필수 여부: 선택
미선택 저장값: NULL
```

기존 시스템 규칙이 없다면 빈 문자열보다 `NULL` 사용을 우선 검토합니다.

### 2.9 기본값

신규 등록 화면을 처음 열었을 때 선택할 코드값을 작성합니다.

```text
기본값: NORMAL
```

사용자가 직접 선택해야 한다면 다음과 같이 작성합니다.

```text
기본값: 없음 — 사용자가 직접 선택
```

화면의 `선택하세요`는 안내 문구이며 실제 DB 코드값으로 저장하지 않습니다.

## 3. 파일 업로드 작성 방법

### 3.1 전체 작성 예시

개발환경에서는 로컬 파일시스템, 운영환경에서는 NAS를 사용하는 예시입니다.

```text
[파일 업로드]

저장 방식: 개발은 파일시스템, 운영은 NAS
개발 저장 경로: ${APP_UPLOAD_DIR:/tmp/springai/uploads}
운영 저장 경로 또는 bucket: ${APP_UPLOAD_DIR:/data/egov/uploads/notice}
파일당 최대 크기: 10MB
최대 파일 수: 게시글당 5개
허용 확장자: pdf, hwp, hwpx, doc, docx, xls, xlsx, png, jpg, jpeg
다운로드 권한: 로그인 사용자만 가능, 비공개 파일은 작성자와 관리자만 가능
악성코드 검사: 운영 내부 백신 검사 후 저장, 개발환경은 미적용
삭제·보존 정책: 논리 삭제 후 30일 보관, 배치 작업으로 물리 삭제
```

### 3.2 저장 방식

다음 저장 방식 중 하나를 선택합니다. 환경별 방식이 다르면 개발과 운영을 분리해 작성합니다.

```text
저장 방식:
- 개발: 로컬 파일시스템
- 운영: NAS
```

| 방식 | 적합한 환경 | 확인할 사항 |
|---|---|---|
| 파일시스템 | 개발환경, 단일 서버 | 재배포 시 보존, 백업, 서버 이중화 |
| NAS | 내부망, 다중 서버 | 마운트 경로, 접근 권한, 장애 대응 |
| S3 | 클라우드, 확장형 환경 | 외부망 승인, 암호화, IAM, 보존 정책 |
| 미정 | 인프라 검토 전 | 운영 배포 전 최종 확정 필요 |

공공기관 망분리 여부가 확인되지 않았다면 다음처럼 보수적으로 작성합니다.

```text
저장 방식:
- 개발: 파일시스템
- 운영: 미정 — 인프라 및 망분리 정책 확인 필요
```

### 3.3 개발 저장 경로

개발 PC 또는 개발 서버에서 업로드 파일을 저장할 경로를 작성합니다.

```text
개발 저장 경로: ${APP_UPLOAD_DIR:/tmp/springai/uploads}
```

프로젝트별 상대 경로를 사용하려면 다음과 같이 작성할 수 있습니다.

```text
개발 저장 경로: ${APP_UPLOAD_DIR:./var/uploads}
```

`src/main/resources/static/uploads`처럼 소스와 사용자 파일이 섞이는 경로는 사용하지 않습니다. 재배포
과정에서 파일이 유실될 수 있고, 접근 권한 검증 없이 정적 URL로 노출될 위험이 있습니다.

경로는 환경변수로 주입하는 방식을 권장합니다. 실제 운영 서버의 민감한 구성정보는 Git에 커밋하지
않습니다.

### 3.4 운영 저장 경로 또는 bucket

파일시스템이나 NAS를 사용하면 절대경로 또는 환경변수 이름을 작성합니다.

```text
운영 저장 경로 또는 bucket: ${APP_UPLOAD_DIR:/data/egov/uploads/notice}
```

S3를 사용하면 버킷명, prefix 및 리전을 작성합니다.

```text
운영 저장 경로 또는 bucket:
- bucket: egov-production-files
- prefix: notice/
- region: ap-northeast-2
```

운영 인프라가 정해지지 않았다면 다음과 같이 기록합니다.

```text
운영 저장 경로 또는 bucket: 미정 — 운영 인프라 담당자 확인 필요
```

Access Key, Secret Key, 비밀번호는 문서에 작성하지 않습니다. 승인된 Secret Manager 또는 운영
환경변수로 주입합니다.

### 3.5 파일당 최대 크기

파일 한 개의 최대 허용 용량을 작성합니다.

```text
파일당 최대 크기: 10MB
```

업무별 초기 검토 기준은 다음과 같습니다.

| 업무 유형 | 예시 한도 |
|---|---:|
| 일반 게시판 | 10MB |
| 이미지 중심 게시판 | 20MB |
| 설계서·대용량 문서 | 50MB |
| 동영상 | 별도 스토리지 정책 필요 |

파일당 크기뿐 아니라 요청 전체 크기도 설정해야 합니다. 파일당 10MB, 최대 5개라면 일반 폼 데이터를
고려해 요청 전체 한도를 60MB로 설정할 수 있습니다.

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 60MB
```

### 3.6 최대 파일 수

게시글 한 건에 첨부할 수 있는 최대 파일 수를 작성합니다.

```text
최대 파일 수: 게시글당 5개
```

화면의 파일 선택 개수뿐 아니라 서버에서도 동일한 제한을 검증해야 합니다. `제한 없음`은 저장소 비용과
서비스 거부 공격 위험이 있으므로 특별한 사유가 없으면 사용하지 않습니다.

### 3.7 허용 확장자

허용할 파일 확장자를 소문자로 작성합니다.

```text
허용 확장자: pdf, hwp, hwpx, doc, docx, xls, xlsx, png, jpg, jpeg
```

이미지 전용 업무는 다음과 같이 제한할 수 있습니다.

```text
허용 확장자: png, jpg, jpeg, webp
```

`exe`, `dll`, `sh`, `bat`, `cmd`, `js`, `jsp`, `php`, `war`, `jar` 등 실행 가능하거나 서버에서 해석될
수 있는 확장자는 차단합니다. 확장자 검사만으로는 충분하지 않으므로 다음 검사를 함께 적용합니다.

- MIME 타입 검사
- 파일 시그니처 검사
- 파일명 정규화 및 경로 탐색 차단
- 서버 공개 경로 외부에 저장
- 서버가 생성한 식별자로 저장 파일명 변경

### 3.8 다운로드 권한

파일을 내려받을 수 있는 주체와 조건을 작성합니다.

```text
다운로드 권한:
- 공개 게시글: 누구나 가능
- 비공개 게시글: 작성자와 관리자만 가능
- 삭제된 게시글: 관리자만 가능
```

회원 전용 게시판이라면 다음처럼 간단히 작성할 수 있습니다.

```text
다운로드 권한: 로그인 사용자만 가능
```

스토리지 URL을 직접 공개하지 않습니다. 다운로드 Controller에서 로그인, 게시글 공개 여부, 소유권 및
관리자 권한을 확인한 후 파일을 스트리밍합니다.

### 3.9 악성코드 검사

업로드 파일에 적용할 백신 또는 악성코드 검사 방식을 작성합니다.

```text
악성코드 검사:
- 개발: 미적용
- 운영: 내부 백신 API 연계
- 악성 파일 또는 검사 실패: 업로드 거부
```

내부 ClamAV를 사용하는 경우에는 다음과 같이 작성합니다.

```text
악성코드 검사: 내부 ClamAV 서버에서 정상 판정 후 최종 저장
```

정책이 정해지지 않았다면 다음과 같이 작성합니다.

```text
악성코드 검사: 미정 — 보안 담당자 확인 필요
```

검사 서버 장애 시 허용할지, 거부할지 또는 임시 격리할지도 함께 결정해야 합니다. 보안 요구가 높은
환경에서는 검사 불능 파일을 정상 파일로 간주하지 않습니다.

### 3.10 삭제·보존 정책

게시글 삭제, 첨부 교체 및 등록 취소 시 실제 파일을 처리하는 방식을 작성합니다.

```text
삭제·보존 정책:
- 게시글 삭제 시 첨부파일을 논리 삭제 상태로 변경
- 실제 파일은 30일간 보관
- 30일 후 배치 작업으로 물리 삭제
- 삭제 이력은 1년간 보관
```

정책에는 다음 상황을 포함해야 합니다.

- 게시글 수정 중 교체된 파일
- 임시 업로드 후 등록이 취소된 파일
- DB에는 없지만 스토리지에 남은 고아 파일
- 백업 파일의 보존 기간
- 개인정보가 포함된 파일의 파기 방식

복구 요구가 없다면 즉시 삭제할 수 있습니다.

```text
삭제·보존 정책: 게시글 삭제 시 DB 메타데이터와 실제 파일을 즉시 삭제
```

감사 또는 법정 보존이 필요하면 승인 주체와 기간을 함께 작성합니다.

```text
삭제·보존 정책:
- 게시글 삭제 후 첨부파일 1년 보존
- 관리자 승인 후 물리 삭제
- 삭제 이력 5년 보관
```

### 4.1 공지사항과 NAS 사용 예시

```text
[공통코드]

업무명: 공지사항 관리
DB/schema: com
게시글 테이블: COMTNBBS
카테고리 컬럼: NOTICE_TYPE_CODE
원하는 카테고리 값:
- 일반공지: NORMAL
- 긴급공지: URGENT
- 시스템점검: MAINTENANCE
기존 CODE_ID: NOTICE_TYPE
필수 여부: 필수
기본값: NORMAL

[파일 업로드]

저장 방식:
- 개발: 파일시스템
- 운영: NAS
개발 저장 경로: ${APP_UPLOAD_DIR:/tmp/springai/uploads}
운영 저장 경로 또는 bucket: ${APP_UPLOAD_DIR:/data/egov/uploads/notice}
파일당 최대 크기: 10MB
최대 파일 수: 게시글당 5개
허용 확장자: pdf, hwp, hwpx, doc, docx, xls, xlsx, png, jpg, jpeg
다운로드 권한:
- 공개 게시글: 누구나 가능
- 비공개 게시글: 작성자와 관리자만 가능
악성코드 검사:
- 개발: 미적용
- 운영: 내부 백신 연계
- 검사 실패 또는 백신 장애: 업로드 거부
삭제·보존 정책:
- 삭제 요청 시 DB에서 논리 삭제
- 실제 파일은 30일간 보관
- 30일 후 배치 작업으로 물리 삭제
- 삭제 이력은 1년간 보관
```

### 4.2 결정된 정보가 적은 경우

확인되지 않은 값을 추측하지 않고 다음과 같이 작성해도 됩니다.

```text
[공통코드]

업무명: 자료실 관리
DB/schema: 모름 — 조회 필요
게시글 테이블: 자료실 업무 테이블 조회 필요
카테고리 컬럼: 기존 분류 컬럼 조회 필요
원하는 카테고리 값:
- 지침
- 서식
- 매뉴얼
기존 CODE_ID: 모름 — 유사 공통코드 조회 필요
필수 여부: 필수
기본값: 없음

[파일 업로드]

저장 방식:
- 개발: 파일시스템
- 운영: 미정
개발 저장 경로: ${APP_UPLOAD_DIR:/tmp/springai/uploads}
운영 저장 경로 또는 bucket: 미정 — 인프라 담당자 확인 필요
파일당 최대 크기: 임시 기준 10MB
최대 파일 수: 임시 기준 5개
허용 확장자: pdf, hwp, hwpx, doc, docx, xls, xlsx
다운로드 권한: 로그인 사용자만 가능
악성코드 검사: 미정 — 보안 담당자 확인 필요
삭제·보존 정책: 임시 기준으로 30일 보관 후 물리 삭제
```

이 상태에서도 읽기 전용 DB 조회, 개발환경 파일 저장 및 기본 검증 구현을 먼저 진행할 수 있습니다.
운영환경 저장소와 보안 기능은 담당자 승인을 받은 후 활성화합니다.

## 5. 제출 전 확인사항

- [ ] 업무 테이블과 공통코드 테이블을 구분하였는가?
- [ ] 카테고리 표시명과 DB 저장 코드값을 함께 작성하였는가?
- [ ] 기존 `CODE_ID`인지 신규 제안인지 구분하였는가?
- [ ] 필수 여부와 기본값이 서로 모순되지 않는가?
- [ ] 개발 저장소와 운영 저장소를 구분하였는가?
- [ ] 파일당 크기와 게시글당 파일 수를 모두 작성하였는가?
- [ ] 확장자뿐 아니라 MIME·시그니처 검사를 고려하였는가?
- [ ] 다운로드 권한을 공개·비공개 상황별로 작성하였는가?
- [ ] 악성코드 검사 실패 시 처리 방법을 작성하였는가?
- [ ] 삭제, 교체, 등록 취소 및 고아 파일 정책을 작성하였는가?
- [ ] 미정 항목에 확인 담당자를 표시하였는가?
- [ ] 비밀번호와 Secret Key를 문서에서 제외하였는가?
